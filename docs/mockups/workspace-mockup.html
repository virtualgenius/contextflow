Workspace: one shareable container holding many maps

GitHub #44. One URL for a class or an organisation. Participants open it, add their own map, and the instructor can open any map from one place. Maps keep their own /p/:id URL. The container has its own /w/:id URL. Fully open, same as today's share model.

Each section shows two or three options. Option marked recommended is Della's pick; the reasons sit under each option. Placeholder naming throughout is "workspace"; see the naming question in the plan.

0. How a workspace relates to maps: four models other tools use

Same question for a class and for an organisation: what is the thing that holds many maps, and can a map be in more than one of them? Boxes are maps, the rounded frame is the container, dashed boxes are bounded contexts inside a map.

A · Flat container · v1
Maps are independent. Each map lives in at most one workspace.
  • As in: a Miro team, a Figma project, an Excalidraw+ workspace, a Google Drive folder.
  • Class: exactly right. Org: fine for "one map per team", weak on the seams between teams.
  • Cheapest to build: registry of map ids and names. This is what the beads describe.
B · Organisation › workspaces › maps
Nesting. A department holds its teams' maps under one roof.
  • As in: Notion teamspaces, Confluence spaces, Jira projects, IcePanel organisation › landscapes.
  • Org: matches the org chart, and that is the problem: the map should show reality, not the org chart.
  • Class: never needed. Adds a level of UI nobody asked for yet. Skip unless a customer asks.
C · Collections (a map can be in many)
Maps stand alone; a collection is a saved list. Payments is in both.
  • As in: playlists, Google Drive labels, GitHub Projects across repos, Linear views.
  • Org: nice for "show leadership these five maps". Class: pointless, every map is in one place.
  • Costs the breadcrumb (which collection is "home"?) and makes "your map" ambiguous. Not v1.
D · One org map, team maps are views of it
Contexts are shared; each team map is a lens. Seams stay visible.
  • As in: C4 / Structurizr (one workspace, many views), IcePanel landscape, GitHub #36 "focused map views".
  • Org: the real prize. Screening → Ledger is a relationship between two teams, and only this model can show it.
  • Class: wrong shape; tables must not share contexts. Big change to the doc model (contexts across docs). Not v1.
Where this lands

Build A now: it is what the class needs on Oct 14 and what an architect needs on day one ("one map per team, one link for the org"). Keep the door open to D, which is where the enterprise value is: the registry already holds map ids, so a later "landscape" map can reference contexts in team maps by (mapId, contextId) and draw the cross-team relationships without moving anything. That is the natural follow-up to #36 and #44 together.

Skip B (org-chart nesting) unless a customer asks; the whole point of a context map is to show reality, not reporting lines. Skip C (many-to-many) because it makes "your map" and "back to workspace" ambiguous, which is exactly what a participant should never have to think about.
